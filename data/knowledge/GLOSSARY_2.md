# 术语解释 Glossary

本文档对 Native Financial / PayCrypto 卡服务平台相关术语进行解释，供机构方开发对接和业务人员参考。

---

## 平台与架构

## CaaS（Card-as-a-Service，卡片即服务）

一种将卡片发行能力以 API 形式提供给第三方机构的服务模式。机构无需自行申请银行牌照或搭建支付基础设施，只需调用平台 API 即可完成 KYC、开卡、充值、冻结等全套操作。Native Financial 即是一家 CaaS 提供商。

---

## 机构（Institution / Merchant）

接入 CaaS 平台的企业客户，又称"机构方"。机构在平台完成注册审核后，通过 API 为其下游用户（持卡人）提供开卡、充值等服务。机构对平台负责，平台不直接与持卡人交互。

---

## 持卡人（Cardholder）

机构发行卡片的最终用户，即实际使用虚拟卡或实体卡进行消费的个人。

---

## Dashboard（控制台）

平台提供的 Web 管理界面，机构用于查看钱包地址、管理 AppKey/Secret、配置 Webhook 等。分测试环境和生产环境两套：

| 环境 | 地址 |
|------|------|
| 测试环境 | https://caas-sandbox.native.financial/ |
| 生产环境 | https://caas.native.financial/ |

---

## Sandbox（沙箱 / 测试环境）

用于开发调试的隔离环境，数据与生产环境完全隔离。Sandbox 中的 AppKey、Secret 和生产环境不通用，且通常有 IP 白名单限制。**尚未签署合同的机构无法申请 Sandbox 账户。**

---

## IP 白名单（IP Whitelist）

平台安全机制之一。只有在 Dashboard 中预先登记的 IP 地址，才能正常访问 API 接口或登录 Dashboard。未登记的 IP 发出的请求会被直接拦截，返回鉴权失败。生产环境和测试环境均需配置。

---

## 身份认证与合规

## KYC（Know Your Customer，了解你的客户）

金融行业监管要求，平台在为用户发卡前须验证其真实身份。不同卡类型对 KYC 级别要求不同：

| 级别 | 所需材料 | 适用场景 |
|------|---------|---------|
| **无 KYC（No KYC）** | 姓名、邮箱、手机号、地址 | UQ Option 1 等低门槛卡 |
| **标准 KYC（Standard KYC）** | 基础信息 + 护照文件上传 | Native 虚拟卡、Native 实体卡、UQ Option 2 |
| **加强 KYC（Enhanced KYC）** | 基础信息 + 护照上传 + 活体认证 | 高权限卡、强合规场景 |

> 已通过低级别 KYC 的用户若申请需要加强 KYC 的卡，**必须重新提交全套材料**。

---

## AML（Anti-Money Laundering，反洗钱）

金融合规要求，平台和机构须监控并报告可疑交易，防止资金被用于洗钱等违法活动。KYC 是 AML 合规的基础环节。

---

## 活体认证（Liveness Check）

一种身份验证技术，要求用户实时完成人脸识别，防止照片或视频欺诈。加强 KYC 级别的卡（如 UQ Option 2）必须完成活体认证，审核时间为 **8～48 小时**。与"自拍持护照"不同：活体认证是自动化的生物特征比对，后者是人工审核。

---

## 自拍持护照（Mix Doc）

标准 KYC 要求的一种材料，即用户手持护照的正面自拍照片（对应参数 `mix_doc`）。区别于活体认证，这是静态图片人工审核，不需要实时视频。Native 虚拟卡和实体卡均需要此材料。

---

## `acct_no`（账户编号）

机构为每个持卡人分配的唯一标识符，全平台唯一。在创建 KYC 记录、申请卡片、充值等 API 调用中，均以 `acct_no` 关联持卡人身份。**不同用户的 `acct_no` 绝对不能重复。**

---

## `cust_tx_id`（客户交易 ID）

机构自行生成的业务流水号，用于标识单次 API 操作（如一次开卡请求）。作为幂等键使用：相同的 `cust_tx_id` 重复提交时，平台只处理一次，可用于防重和对账。

---

## API 认证

## AppKey / App Key

机构在 Dashboard 创建的 API 访问标识，类似"用户名"，随每次 API 请求一起发送，用于标识来自哪个机构。**AppKey 本身不作为签名密钥，不具保密要求，但不应随意公开。**

---

## Secret / Secret Key

与 AppKey 配套的私密密钥，用于生成 HMAC 签名。**Secret 只在创建时显示一次，丢失后无法找回，需重新生成（旧 Secret 立即失效）。** 绝对不能提交到代码库或暴露给前端。

---

## HMAC（Hash-based Message Authentication Code，基于哈希的消息认证码）

一种利用密钥对请求内容进行签名的算法，本平台使用 `HMAC-SHA256`。机构将请求参数 + 时间戳等内容用 Secret 签名后附在请求头中，平台用相同算法验证，确保请求未被篡改且来自合法机构。

**签名流程简述：**
1. 将请求体（JSON 字符串）+ 时间戳等拼接成待签字符串
2. 用 `HMAC-SHA256(Secret, 待签字符串)` 计算签名
3. 将签名放入请求头（如 `X-Signature`）随请求发送

---

## Webhook（回调通知）

平台在卡片状态发生变更时，主动向机构预配置的 URL 推送 HTTP POST 请求的机制。常见触发事件：KYC 审核完成、卡片激活、充值到账等。机构无需轮询接口，通过 Webhook 即可实时获知状态变化。

> ⚠️ 生产环境中应对 Webhook 推送的内容做签名验证，防止伪造请求。

---

## 卡片相关

## 虚拟卡（Virtual Card）

无实体形态的数字卡片，包含卡号、有效期、CVV 等信息，可直接用于线上支付。发卡即时，无物流环节。Native 虚拟卡和 UQ 虚拟卡都属于虚拟卡。

---

## 实体卡（Physical Card）

有实体形态的塑料卡片，可用于线下 POS 刷卡和 ATM 取现，同时支持 Apple Pay。申请时须提供卡号参数（`card_number`），发卡后需等待物流寄送。KYC 要求与虚拟卡一致。

---

## `card_type_id`（卡类型 ID）

平台为每种卡片配置的唯一类型编号，申请卡时必须传入。不同卡类型对应不同的 BIN、功能支持和费率。机构在开始对接时需向平台确认可用的 `card_type_id` 清单。

---

## `card_no`（卡号）

持卡人的支付卡号。卡片**未激活**时返回脱敏格式（末四位显示为 `****`）；**激活后**返回完整明文卡号。实体卡申请时需要预先传入卡号，虚拟卡则由平台生成。

---

## BIN（Bank Identification Number，银行识别号）

卡号前 6～8 位数字，用于标识发卡机构、卡组织（Visa/Mastercard）、卡片类型（借记/预付）等信息。平台根据不同 BIN 提供不同的卡片产品，机构一般不需要直接操作 BIN，但了解 BIN 有助于判断卡片的网络支持范围。

---

## Apple Pay / Google Pay

手机移动支付方式，将虚拟卡绑定到手机钱包，用于线下 NFC 支付。**Native 虚拟卡和 UQ Option 2 支持 Apple Pay；UQ Option 1 不支持。**

---

## 卡片激活（Card Activation）

卡片发行后默认处于未激活状态，无法使用。机构须调用激活 API（虚拟卡和实体卡使用同一套接口）将卡片激活后，持卡人才能正常消费。激活后 `card_no` 的脱敏符 `****` 替换为真实末四位。

---

## 卡片冻结 / 解冻（Freeze / Unfreeze）

通过 API 临时禁用或恢复卡片的消费功能。冻结期间卡片无法交易，解冻后恢复正常。**支持 API 操作。**

---

## 卡片注销（Cancel / Close Card）

永久停止卡片使用。注销后无法恢复。**该操作目前不支持 API，必须联系平台人工处理。**

---

## 资金与结算

## 卡申请资金池（Card Application Fund）

机构钱包中专门用于支付**办卡手续费**的资金池。每次申请新卡时，平台自动从此账户扣除费用（如 JDB 卡 $103）。此账户余额不足时无法开卡。

---

## 卡充值资金池（Card Top-Up Fund）

机构钱包中专门用于**为持卡人卡片充值**的资金池。每次为用户卡片充值时，平台从此账户扣除对应金额。与卡申请资金池相互独立，**两池之间的划转仅平台方可操作**。

---

## USDT / USDC（稳定币）

与美元 1:1 挂钩的加密货币：
- **USDT（Tether）**：目前最主流的稳定币，发行在多个区块链网络（TRC-20、ERC-20 等）
- **USDC（USD Coin）**：由 Circle 发行的美元稳定币，合规性较高

机构通过向平台提供的钱包地址充入稳定币，用于办卡和卡片充值。**充值前须确认链类型一致（如 TRC-20 地址只能充 TRC-20 的 USDT），链类型不匹配可能导致资金丢失。**

---

## TRC-20 / ERC-20 / BEP-20（区块链网络协议）

稳定币所在的不同区块链网络：

| 协议 | 区块链 | 特点 |
|------|--------|------|
| **TRC-20** | TRON 波场 | 手续费极低，转账速度快，常用于大额充值 |
| **ERC-20** | Ethereum 以太坊 | 安全性高，但 Gas 费较高 |
| **BEP-20** | BNB Chain | 手续费较低，兼容以太坊生态 |

**充值时必须使用与钱包地址匹配的网络，否则资金可能永久丢失。**

---

## 区块确认数（Block Confirmations）

区块链交易在被纳入区块后，后续每新增一个区块即为一次"确认"。平台通常要求达到一定数量的确认后才认为充值到账，以防止双花攻击。不同区块链的确认速度和平台要求不同，一般在 1～20 个确认之间。充值到账后平台自动入账，无需人工干预。

---

## Gas 费（Transaction Fee）

在以太坊等区块链上发送交易时，支付给矿工/验证者的手续费，以 Gas 计算。Gas 费与网络拥堵程度相关，不受平台控制。TRC-20（TRON）的手续费极低，是 USDT 充值的常用选择。

---

## 卡片消费相关

## EUR 卡 / USD 卡

按卡片结算货币划分的两类卡：

- **USD 卡**：以美元结算，适合全球美元消费场景
- **EUR 卡**：以欧元结算，要求 KYC 中的地址信息填写欧洲国家地址（`country`、`city` 等字段须为欧洲国家），护照图片大小限制为 **1MB**（USD 卡为 2MB）

---

## 支付宝绑定（Alipay Binding）

指将虚拟卡添加为支付宝付款方式，供中国大陆用户在支付宝生态内消费。**仅 UQ 虚拟卡 Option 1 和 Option 2 支持此功能**，Native 卡均不支持。

---

## ATM 取款（ATM Withdrawal）

使用实体卡（或部分虚拟卡）在 ATM 机上提取现金。平台对不同卡种设有单笔、日、月限额，且收取手续费（Native 卡 4%+$0.99，UQ 卡 2% 最低 $1，JDB 卡 0.75%）。

---

## 敏感信息（Sensitive Card Data）

包含卡号（`card_no`）、CVV、有效期等，只能通过平台提供的专用敏感信息查询接口获取，不会出现在普通查询接口的返回中。参考代码见 `BankTest.java#L90`。

---

## 生产上线注意事项

## 幂等性（Idempotency）

API 接口的设计特性，指使用相同的 `cust_tx_id` 多次发送请求，只有第一次生效，后续重复请求不会创建新的记录。机构在网络超时重试时，必须使用相同的 `cust_tx_id`，**不可用不同 ID 重试同一笔业务，否则会产生重复操作。**

---

## Secret 泄露处置

若 Secret Key 疑似泄露，需立即在 Dashboard 重新生成新 Secret。**旧 Secret 立即失效**，需同步更新所有调用方的配置，否则 API 调用会返回 401 认证失败。

---

## Webhook 重试机制

平台在推送 Webhook 失败（如机构服务器无响应或返回非 2xx）时，会进行一定次数的重试。机构应：
1. 对 Webhook 做**幂等处理**（同一事件 ID 只处理一次）
2. 快速返回 `200 OK`，耗时操作异步处理
3. 对 Webhook 消息做**签名验证**，防止伪造请求

---

## 环境隔离

测试环境（Sandbox）与生产环境完全隔离，数据、AppKey/Secret 均不互通。上线前须将所有配置（API 域名、Dashboard 地址、AppKey、Secret）切换为生产环境值，并重新申请 IP 白名单。

---

## 资金池余额预警

生产环境中应实时监控「卡申请资金池」和「卡充值资金池」余额，在余额不足时及时充值，避免开卡或充值操作因余额不足而失败。建议提前储备数日业务量的资金。

---

## 签名时钟偏差（Timestamp Skew）

HMAC 签名中包含时间戳，平台会校验请求时间与服务器时间的偏差。**偏差通常不应超过 5 分钟**，超时请求会被拒绝（返回 401）。生产服务器应使用 NTP 校准系统时间，防止时钟漂移导致批量请求失败。
